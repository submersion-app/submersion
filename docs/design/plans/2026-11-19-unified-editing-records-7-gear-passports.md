# Unified editing, phase 3, plan 7: gear items, the passports as satellites, twin sets, components, findings in the change log Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Finish the gear item behind `kUnlockRecordEditing` (issue #4527, phase 3). The cards plan 6 left read only (Twin set, Components, Condition findings) are held in the item's sitting. `equipment_findings` joins the change log, so a dismissal is in the item's History entry. The cylinder passport and the gear passport become satellite pages of the item. Opened alone they open locked and have their own Unlock, Cancel and Save. Pushed from an unlocked item page they join its sitting. Everything they write today (fills, twin fills, O2 clean, a linked tag, trip packing, clocks, moves) is held.

**Architecture:** As plan 6. The item page's sitting code (what `onSittingStart` loads, `saveSitting` with its media undo and `afterGearItemSave`) moves out of the page's part file into a mixin, `GearItemSittingHost`. The item page and both passports use it, so a passport opened alone saves exactly as the item page does: one `writeRecordSitting` labelled `record_edit:equipment:<id>:<cards>`. The passports join a sitting through plan 1's `joinedSitting` and `pushRecordSatellite`. Collections are `SittingList`s. Replays that must check the whole table again at Save (pairings, a tag link) are held changes that run through the repository inside the transaction and turn its refusal into a `RecordSittingRefusal`. The findings change follows phase 1 plan 9: `equipment_findings` becomes `deleteCopyOnly` with an opt-in update trigger on `dismissed_at` only, regenerated by hash on open, so there is no migration rung.

**Tech Stack:** Flutter, Riverpod (`flutter_riverpod`), drift, go_router, `flutter gen-l10n`.

**Spec:** [docs/design/specs/2026-11-18-unified-editing-phase-3-records-design.md](../specs/2026-11-18-unified-editing-phase-3-records-design.md), sections "Design: gear items" (the Twin set, Condition findings and Components rows, "Held writes", "Passports"), "Design: what is generalised" (satellite pages), "Design: rules every phase 3 type follows" (writes on viewing), "Calls made in this note", "Testing" and "Delivery". It builds on [records-1](2026-11-19-unified-editing-records-1-shared.md) (satellite host), [records-6](2026-11-19-unified-editing-records-6-gear-cards.md) (gear item cards) and the dive History plan ([unified-editing-9](2026-11-16-unified-editing-9-history.md)) for the findings' change log shape.

## Questions for Eric

The plan is written to the recommended answer of each; a different answer changes only the task named.

1. **How a dismissal is logged** (the note's call "Logging a finding's dismissal adds `equipment_findings` to the change log"). **Recommended:** as the dive safety findings are. The table is delete-copy-only with an update trigger that records `dismissed_at` only, and only inside a sitting, an agent write or a revert. The background recompute, which rewrites findings constantly, never makes History entries, and a deleted item's findings keep their delete copies so a restore brings back its dismissals. The other way: fully tracked, which would log every recompute as manual History entries on the item. (Task 1.)
2. **A tag scan's fill import and the passport id minted on open stay outside the rule** (a call in the note). **Recommended:** keep both. The import runs before the page opens and is its own History entry, as today. The mint derives the id from the item's id and is a write on viewing. The other way: hold the import in a sitting the scan opens, which would make a scan open the page unlocked. (Tasks 8, 9.)
3. **A passport opened from a locked item page.** Decision 4 says a passport opened alone opens locked with its own lock, and one pushed from an unlocked item page joins its sitting. **Recommended:** opened from a locked item page it is "alone": it has its own lock, its Save writes one entry on the item, and the item page under it follows the stored item (plan 1's tested behaviour). The other way: the entry card unlocks the item page first, then pushes the passport joined. (Task 9.)
4. **Writing a fill to the NFC tag.** Today, after a fill is logged, the passport offers to write it to the tag. **Recommended:** in a sitting the offer comes after Save, for the fills the sitting logged, from the page that saved. Writing the tag at log time would put a fill on the cylinder that Cancel then discards from the log. The other way: offer it at log time, as today. (Task 7.)
5. **The Twin set card while Worn as changes in the sitting.** **Recommended:** the card follows the sitting's Worn as. If the diver sets Twin set on Details and the cylinder has no pairing, the card hides, as it would after Save. The other way: it follows the stored item until Save. (Task 4.)
6. **Which dives a component change rewrites.** Each add, replace or remove asks "Update past dives?" when it is made, as today. **Recommended:** at Save the dives are rewritten from the net change of each part against the stored assembly, using the last answer given for that part. A part added and removed in one sitting changes no dive. The other way: replay every step with its answer in order, which can leave a part on logged dives it is no longer in. (Task 5.)
7. **Values calculated from components and fills while unlocked.** **Recommended:** the assembly totals, the parts' service dots and the passport's Usage card stay as stored until Save, as plan 6 did for clock statuses. The current fill follows the sitting's fills, because that is the value being edited. The other way: a live preview of the totals from the held parts. (Tasks 5, 7.)
8. **One pull request.** **Recommended:** one PR, built and reviewed as one, about plan 6's size. The other way: two, Tasks 1 to 5 (findings, twin set, components) and then Tasks 6 to 9 (passports). (Task 10.)
9. **#4641 is open again.** It was reopened after #4652 shipped the "Worn as: Twin set" mark. **Recommended:** plan 7 builds nothing for it beyond Question 5; whatever keeps it open is its own work. The other way: say what is left, and whether it belongs here.

## Calls made in this plan, for Eric to check

1. **Track O2 clean** on the cylinder passport adds a held clock to the item's service clocks, so History names it Service clocks, the card that owns clocks. The passport's Service card is framed as the item's `serviceClocks` card on that page, and `GearItemCardId.passportService` stays unused. Its name can never be reused, since ids are never renamed.
2. **A twin fill's partner** has its passport id minted at Save, inside the sitting's transaction, when it has none (`TwinFillService.recordTwinFill` does it today in its own write). That write is in the same History entry.
3. **A pairing's History.** A pairing row is logged under its first cylinder. A sitting's entry is pinned to the item it edits. So a pairing changed from either cylinder's page shows in that page's entry and also in the first cylinder's History. Today it shows only in the first cylinder's.
4. **Refusals at Save.** A held pairing that now clashes, a tag another fitted item now holds, or a component that would now make a cycle fails the whole Save with today's message (`twinSet_clashBody`, `passport_tag_linkInUse`, `equipment_components_cycleError`), writes nothing and leaves the page unlocked.
5. **A finding gone by Save.** A held dismiss or restore of a finding a recompute has since deleted is skipped, not an error, as on dives.
6. **A recompute during Save.** One that clears a dismissal while the sitting's transaction runs is recorded in that sitting's entry, because the change log context is one row. Dive safety findings behave the same way.
7. **Reverting a dismissal reaches other devices.** `equipment_findings` has no clock of its own; its rows ride on the item's. A revert today marks only the reverted row pending, so other devices would never receive it. The revert also marks the item pending (Task 1).
8. **New trip from the Pack card** creates the trip at once, which survives Cancel, as any record created from a picker does. Packing the item for it is held.
9. **Fills logged from the gas blender's procedure card** keep writing at once. It is another tool, not the passport.
10. **"See all" on the gear passport's Recent service** opens the item's own page. It is hidden while the passport holds a sitting of its own, so no second sitting can be opened on the same item. Locked, or joined, it works as today.
11. **A fill logged in the sitting carries the passport id the sitting shows** (a tag linked in the same sitting included). At Save the link's re-keying moves every older fill, so all of them end on the new id in either order (Review Focus 1).
12. **The passports stay full pages,** with no pane and no edit address. Their routes gain `onExit: confirmLeaveRecordSitting`.
